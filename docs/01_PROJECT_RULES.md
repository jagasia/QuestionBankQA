# Project Rules: The Constitution of QuestionBankQA

This document establishes the binding architectural, design, and implementation rules for **QuestionBankQA**. Every future design document, code contribution, and refactoring effort must comply with these guidelines. 

---

## 1. Core Rules

### Rule 1: Never Hardcode Excel Column Names
*   **Statement**: The application must never rely on fixed spreadsheet headers (e.g., `Question Text`, `Answer Choice 1`, `Correct Answer`).
*   **Rationale**: Different clients use vastly different layouts, header vocabularies, and column orderings. Hardcoding headers prevents the tool from scaling to new clients without code modifications.
*   **Implementation**:
    *   All external schemas must map to the internal representation via a dynamic configuration template.
    *   Column headers must be parsed dynamically using semantic matching (via LLM/embeddings) or user-defined explicit mappings.

---

### Rule 2: Never Discard Unknown Client Data
*   **Statement**: Columns and metadata present in the client's imported file that do not map to the Canonical Question Model must not be lost or omitted.
*   **Rationale**: Client workbooks often contain custom columns (e.g., internal IDs, creator names, tracking codes, or custom taxonomy classifications) that must be returned untouched when the reviewed file is exported.
*   **Implementation**:
    *   Implement a structured `metadata` or `extensible_attributes` container (as a key-value map) within the import adapter.
    *   Retain the original row indices and unmapped cells.
    *   The Export Engine must merge these preserved columns back into the correct rows during export.

---

### Rule 3: Configuration-Driven Architecture
*   **Statement**: All validation rules, import mapping definitions, export formatting, and target schema mappings must be stored as configurations, not written as procedural code.
*   **Rationale**: Adding a new client or modifying a QA checklist should require changing a config document, not deploying new code.
*   **Implementation**:
    *   Store client-specific layouts, parsing rules, and rulesets in JSON or YAML configuration objects.
    *   Validation engines must read rulesets from a configuration store and validate data dynamically.

---

### Rule 4: Explainable AI with Confidence Metrics
*   **Statement**: Every recommendation, error classification, or correction generated by the Gemini API must be accompanied by its reasoning and a confidence score.
*   **Rationale**: Human review is the final approval step. To review efficiently, the human needs to understand *why* the AI flagged a question or suggested a change.
*   **Implementation**:
    *   Structured JSON outputs from the LLM must contain a `reasoning` string (in markdown format explaining the rule violation) and a `confidence` float (scaled 0.0 to 1.0).
    *   Display these reasons visually in the Review Engine UI.

---

### Rule 5: Canonical First Operations
*   **Statement**: All core engines, logic, checklists, and AI analyses must operate strictly on the Canonical Question Model.
*   **Rationale**: Decoupling the data format of the source files from the business logic prevents changes in import/export formats from breaking validation or UI rules.
*   **Implementation**:
    *   Import adapter: `External File -> Canonical Question Model`
    *   Core logic: `Canonical Question Model -> Operations -> Canonical Question Model`
    *   Export adapter: `Canonical Question Model -> External File`
    *   No utility outside of the Import/Export adapters should ever touch raw Excel rows or column names directly.

---

### Rule 6: First-Class Import and Export Modules
*   **Statement**: Import and Export are primary architectural components of the codebase, not helper utilities or background scripts.
*   **Rationale**: The business value of QuestionBankQA is centered on its ability to ingest messy external workbooks and return them with 100% layout fidelity. Treating them as afterthoughts leads to fragile, unmaintainable parsers.
*   **Implementation**:
    *   Dedicate separate directory structures and modules to the `Import Engine` and the `Export Engine`.
    *   Write isolated unit and regression tests specifically for import mappings and export rendering.

---

### Rule 7: Backward Compatibility of Mappings and Templates
*   **Statement**: Updates to the database schema, canonical models, or codebase must not break existing mapping templates saved by users.
*   **Rationale**: Clients upload data in batches. If an update invalidates their previously saved mapping templates, they will have to map their columns again from scratch, causing frustration.
*   **Implementation**:
    *   Apply versioning to templates.
    *   Write migration scripts or fallback resolvers for old templates when schema alterations occur.

---

### Rule 8: Strict UI and Business Logic Separation (MVC)
*   **Statement**: UI layers and components must never execute business rules, parsing logic, or direct database mutations.
*   **Rationale**: Ensures portability of the codebase (e.g., swapping a UI framework or executing validation pipelines in batch CLI environments) and guarantees clean testability.
*   **Implementation**:
    *   UI components must act as pure views, binding to state and invoking controllers or hooks.
    *   Validation, transformation, and AI routines must be encapsulated in testable, pure-JS/TS files or services.

---

### Rule 9: Extensible, Non-Rigid Firestore Schemas
*   **Statement**: Database schemas (particularly in Firestore) must be designed to be extensible and schema-flexible, avoiding strict tabular rigidity.
*   **Rationale**: Different question types (MCQ, Multiple Response, Drag-and-Drop) and different client metadata fields require different attributes. A rigid schema would block support for new item types.
*   **Implementation**:
    *   Use nested documents or flexible map fields for question content and options.
    *   Do not rely on flat databases. Maintain a core set of indexing fields (e.g., `id`, `campaignId`, `status`, `updatedAt`) and store custom or model-specific fields inside an open-ended map.

---

### Rule 10: Document All Architectural Decisions (ADR)
*   **Statement**: Any changes, deviations, or significant additions to the application's architecture must be documented in [03_ARCHITECTURAL_DECISIONS.md](file:///d:/Jag/UpSkilliT/projects/QuestionBankQA-1/docs/03_ARCHITECTURAL_DECISIONS.md) before execution.
*   **Rationale**: Ensures there is a clear log of the design context, alternatives considered, and reasoning behind architectural choices.
*   **Implementation**:
    *   Create a simple log template showing: `Title`, `Date`, `Context`, `Decision`, `Consequences`.
    *   Do not merge PRs affecting architecture without an accompanying entry in `03_ARCHITECTURAL_DECISIONS.md`.

---

## 2. Conflict Resolution and Guidance for AI Assistants

1.  **Do Not Invent Requirements**: Work only with explicit features. If something is not mentioned, check if it fits the MVP boundaries. If it does not, raise it as a recommendation for future releases.
2.  **No Contradictions**: Check current docs before altering logic. If a requested change contradicts the rules defined here, stop and ask the user for clarification.
3.  **Ambiguity Protocol**: If a file layout or business rule is ambiguous, ask the user. Do not guess.
